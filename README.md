# Spotial 웹앱 구현 계획

목표는 iPhone 17 Pro의 Safari에서 Olivia의 저장 자료가 현재 맥락에 맞게 다시 쓰이는 경험을 시연하는 것이다. 첫 번째 구현 단위는 **하나의 저장에서 원본까지 왕복할 수 있는 Spotlight 한 개**다. 화면을 늘리기 전에 한 건의 수정이 Feed, Summary, Full, Source View에 일관되게 반영되는지 확인한다.

## 1. 무엇을 저장하고 무엇을 계산할까

| 단위 | 필드와 책임 | 수명 |
| --- | --- | --- |
| 저장 기록 `Save` | `id, ownerId, savedAt, savedAtPlaceId?, sourceApp, sourceItemId, kind, payload, savedScreenAssetId, appScreenAssetId`. 본문·인용·사진·영상 시점 등 저장 당시 원문을 보관한다. 대상 장소와 사람은 별도의 `entityIds`로 연결한다. | 버전 관리하는 로컬 픽스처 |
| 청크 `Chunk` | `id, saveId, variant, facts, entityIds, tags`. 저장 한 건을 의미 단위 하나로 정규화한다. 메시지 인용은 노트, 장소 핀은 지도, 기사·영상은 콘텐츠, 사진은 이미지로 매핑한다. 앱 이름 하나만으로 유형을 결정하지 않는다. | 저장에서 파생. 1차는 저장당 대표 청크 하나 |
| 현재 맥락 `Context` | 현재 시각·장소·사용 중인 앱·의도, 마지막 요청에서 해석한 장소·사람·조건. 헤더의 칩과 문장은 이 객체 하나를 읽는다. | 시연 세션 |
| 맥락덩어리 `Spotlight` | `id, subjectId, intent, chunkIds, heroChunkId, theme`. 같은 장소·주제·행동을 설명할 자료를 묶는다. 제목·테마는 깊이가 바뀌어도 유지한다. | 맥락과 자료 풀에서 계산 |
| 화면 표현 | Feed는 정렬된 Spotlight 목록, Summary는 선택한 묶음의 Pill, Full은 같은 묶음의 청크 전체, Source View는 선택한 저장의 원본이다. Pill은 `kind, value, sourceChunkIds, action?`를 가진다. | 렌더링할 때 파생 |

Olivia가 집에서 친구의 메시지를 저장했다면 **저장 위치는 집**, 메시지가 가리키는 **대상 위치는 피자집**이다. 인근 추천은 대상 위치로 계산한다. 반대로 “집에서 저장한 것”은 저장 위치로 찾는다. 현재 앱이 Maps여도 해당 인용의 출처는 Messages로 남는다.

시간은 UTC 오프셋이 있는 값으로 기록하고 장소에는 시간대를 둔다. 위치·영업시간·출처 화면이 없는 경우도 허용한다. 값이 없는 Pill과 사용할 수 없는 CTA는 생략한다. 스크린 이미지는 저장 당시 화면과 앱 안의 목적지를 각각 등록한다. 렌더러는 이미지 파일명으로 목적지를 추론하지 않는다.

## 2. 두 기본 맥락과 첫 데이터 묶음

아래 ID와 저장 예시는 제작용 제안이다. 시연 데이터에서 장소 간 도보 시간과 일몰 시각을 고정하면 네트워크와 시연 당일 날씨에 관계없이 같은 장면을 검증할 수 있다.

| | 지도 앱으로 피자집 근처를 지남 | 촬영 후 Camera·Gallery를 보고 있음 |
| --- | --- | --- |
| 기본 맥락 | Sydney 여행 중, Surry Hills 인근, Maps, Eat | Sydney Harbour 인근, Camera 또는 Gallery, 촬영·구도 참고 |
| 최초 저장 자료 | 친구의 추천 메시지, 같은 가게 지도 핀, 가게 리뷰, 메뉴 사진 | 촬영 위치 핀, 구도에 대한 노트, 촬영 레퍼런스 기사, 저장한 사진들 |
| 첫 Spotlight | Jordan’s Pizza Pick. 친구·가게·메뉴가 같은 장소 ID로 연결된다. | Harbour Sunset View. 장소·촬영 지점·구도에 관한 자료가 연결된다. |
| Summary에 남길 근거 | 지도에서 거리, 메시지에서 추천 메뉴, 목적지에서 길찾기 액션 | 위치에서 도보 시간, 시연 시간표에서 일몰, 노트에서 촬영 단서 |
| 요청으로 바꿀 초점 | “친구가 뭐 시키랬지?” → 같은 묶음에서 인용·메뉴를 앞으로 | “아까 찍은 위치”는 내 촬영본·지도, “저장한 구도”는 레퍼런스 사진·기사를 우선 |

예를 들어 `save-msg-01`의 마르게리타 추천 → `chunk-note-01` → 지도 청크와 함께 `spot-pizza` 구성 → Summary의 추천 메뉴 Pill → Full에서 검정 타이틀의 노트 선택 → 해당 메시지 위치의 앱 이미지 순으로 이어진다. 같은 Spotlight에서 메뉴 사진을 선택하면 저장 날짜와 앱 이름이 있는 Source View를 먼저 연다. **메시지 인용을 한 번 수정한 뒤 Feed 설명·Pill·Full 노트에서 함께 바뀌는지**가 첫 통합 검사다.

## 3. 조합과 자유 요청 처리

1. Olivia의 저장 기록을 불러와 참조 무결성을 검사한다. 저장 ID 중복, 없는 장소·청크·이미지 참조, 다른 사람의 저장 참조를 검출한다.
2. 텍스트 입력과 음성 전사의 최종 결과를 같은 해석 함수에 넣는다. “피자집/피자 가게”, “사진 구도/어떻게 찍었지” 같은 표현을 장소·앱·사람·의도·요청 조건으로 정규화한다. 음성 중간 전사는 화면에만 표시한다.
3. 명시된 조건을 먼저 적용하고 대상 장소나 촬영 지점 ID로 후보를 묶는다. 같은 동네에 있다는 이유만으로 다른 식당의 메뉴와 리뷰를 섞지 않는다. 시간 조건에는 저장 시각과 콘텐츠 속 시각 중 질문이 가리키는 값을 사용한다.
4. 후보 묶음은 **명시한 대상·요청 적합도 → 현재 상황에서 실행 가능성 → 현재 위치와의 관련성 → 최근성** 순서로 비교한다. 동률 정렬은 고정 ID로 재현한다. 서로 다른 후보가 요청상 구별되지 않으면 사용자가 선택할 단서 하나를 되묻는다. UI에는 내부 점수를 표시하지 않는다.
5. 묶음 안에서는 요청에 답할 근거를 우선하고 같은 저장의 중복 노출을 줄인다. Feed에는 다른 의도나 정보 조합을 가진 후보만 추가한다. Summary의 2×3 영역은 가용 근거로 채우고, Full에는 선택한 전체 청크를 유지한다. 여러 사진을 가로로 묶어도 각 사진의 저장 ID를 보존한다.
6. 결과가 없으면 직전 Feed와 스크롤 위치를 유지하고 가능한 재질문을 제시한다. 유효한 요청만 새 Feed를 확정한다. 단순 Summary 재생성은 이미지 배열을 유지하면서 Pill의 순서·내용을 바꾼다.

**1차 기술 선택**은 정적 JSON·로컬 이미지, 타입이 있는 조합 함수, React 화면, 브라우저 세션 상태다. 백엔드 DB와 생성형 AI 없이 위 두 경우의 결과를 먼저 재현한다. 실제 기기에서 음성 권한·중간 전사·종료를 초기에 시험하고 텍스트 입력과 같은 결과까지 확인한다. 발화 실패를 기록할 때는 전사 오류, 해석 오류, 저장 자료 부족을 구분한다. 해석 오류가 반복될 때만 제한된 의도·엔티티를 반환하는 모델 API를 검토한다. 데이터 부족은 새 저장을 추가해 해결한다.

## 4. 화면과 제스처 계약

| 조작 | 결과와 보존할 상태 |
| --- | --- |
| Device 화면의 Spot을 안쪽으로 당김 | Spotialize에서 진입 앱과 선택된 자료를 보여준 뒤 Feed의 첫 후보로 이동 |
| 상단 토글 전환 | 같은 현재 맥락을 AT·FROM·FOR 칩 또는 한 문장으로 표시. 선택 카드와 스크롤 위치 유지 |
| Feed → Summary → Full, 역방향 | 핸들 내림·핀치 확대는 한 단계 확장, 핸들 올림·핀치 축소는 한 단계 복귀. 한 번의 입력으로 두 단계를 넘지 않는다. |
| Summary 본문을 세로로 밂 | 같은 카드가 접히며 Feed 스크롤에 연결. Full 본문의 세로 스크롤은 청크 탐색에 사용 |
| Full에서 지도·노트 선택 | 검정 타이틀로 구별되는 CTA. 해당 저장의 목적지 앱 이미지로 직접 이동 |
| Full에서 콘텐츠·이미지 또는 대표 사진 선택 | 해당 저장의 Source View를 열어 출처·저장 날짜와 중앙 원본을 표시. 다시 선택하면 앱 이미지로 이동 |
| 뒤로 가기·제스처 취소 | 들어온 경로, 선택 청크, Full 세로 위치와 사진 스택의 가로 위치 복원 |

화면 상태에는 `depth, spotlightId, chunkId?, feedIndex, scrollOffsets`를 둔다. 드래그·핀치 중간 진행률은 임시값이다. 손을 놓아 단계가 확정될 때만 화면 상태를 갱신한다. 가로 사진 스택, 본문 세로 스크롤, 핸들, 두 손가락 입력은 시작 영역·손가락 수·방향으로 구분한다. CTA를 누른 채 스크롤했을 때 탭까지 발생하지 않아야 한다.

## 5. Figma를 구현에 옮기는 기준

- 기준 프레임은 440×956, 규격서의 17 Pro 설계 뷰포트는 402×874다. 화면 전체를 이미지로 축소하지 않고 폭 기준으로 치수를 환산하고 Safari의 실제 가용 높이·안전 영역 안에 입력과 핸들을 배치한다. 상단 시간·장소와 하단 입력은 유지하고 Full 본문만 세로로 흐르게 한다.
- Feed 384×406과 Summary 384×610은 한 카드다. 동일한 제목·이미지·핸들에 동일한 ID를 부여하고 손가락 진행률로 위치와 크기를 보간한다. Feed는 우하단 핸들 하나, Summary는 우상단·좌하단, Full은 기기 모서리 안쪽을 기준으로 한다. 확장 버튼도 같은 상태 전환을 호출한다.
- Full은 기준 폭 200의 두 열, 간격 4–5다. 기본 R54·스무딩 60%를 사용하고 **각 청크에서 인접한 모서리 최대 한 곳만 R20**으로 바꾼다. 개별 모서리 값은 레이아웃 결과에 둔다. 여러 이웃이 있을 때는 Figma 참조 배치에서 지정한 모서리를 우선하고, 신규 배치는 별도로 검수한다.
- 카드 상단은 #BAFF71, 하단은 대표 이미지 색이다. 같은 Spotlight는 모든 깊이에서 같은 테마를 쓴다. Full은 공통 그라디언트를 타일 좌표에 맞춰 잘라내므로 위젯 경계 양쪽의 색이 이어진다. 글래스·Spotial Active·하단 진행형 블러는 각각 독립 레이어로 비교한다.
- Full의 쉐도잉 청크는 1차에서 도보 시간·일몰 등 출처 있는 사실을 모은 파생 표현으로 제안한다. 구성 설명의 숫자는 실제 묶음의 고유 저장 ID에서 계산한다. 두 표현의 표시를 위해 가상의 원본 저장을 추가하지 않는다.

## 6. 작업 분담과 머지 기준

| 순서 | 담당 | 납품 및 통과 조건 |
| --- | --- | --- |
| 1. 공통 데이터 계약 | 성원 조율, 예주·정헌 대조 | 저장·청크·맥락·Spotlight·목적지 타입과 피자 예시를 공유한다. 세 사람의 새 작업 브랜치가 같은 깨끗한 기준 커밋에서 출발하는지 확인한다. |
| 2. 최소 데이터와 Full | 예주 | 피자 사례의 네 유형과 실제 용도의 이미지 준비. 원본 ID 추적, 두 종류의 탭 경로, 뒤로 복귀를 검증한다. |
| 2. 추천과 입력 | 정헌 | 공유 예시만으로 순위·Pill 선택·재질문을 함수 단위로 검증한다. 미리 준비한 전사문으로 먼저 연결하고 같은 경로에 마이크를 붙인다. |
| 2. 진입과 탐색 | 성원 | 같은 예시로 Device → Feed → Summary → Full을 연결한다. 제스처 중단·역전·스크롤을 검증하고 실제 청크·추천 모듈을 연결한다. |
| 3. 두 기본 맥락 통합 | 세 사람 | 피자와 촬영 각각에서 기본 추천, 다른 표현의 같은 질문, 의도 변경, 모호한 질문, 없는 자료 요청을 통과한다. 매번 Pill 값에서 근거 저장까지 추적할 수 있어야 한다. |
| 4. 시연 품질 확인 후 풀 확장 | 성원 통합, 예주 자료, 정헌 회귀검사 | 17 Pro Safari에서 주소 막대·키보드·음성 권한·핀치 충돌·연속 스크롤을 확인한다. 이후 다른 가게나 다른 촬영 지점을 하나씩 추가하고 기존 질문의 결과도 재검증한다. |

**첫 실기기 결정 사항**은 인접 모서리 선택이 복잡한 배치에서의 우선순위, 글래스와 블러의 가독성·스크롤 성능, 음성 인식 방식이다. 먼저 지도·노트·이미지·콘텐츠가 한 화면에 있는 Full과 그 Summary를 같은 데이터로 열어 디자인을 대조한다. 표현 품질이 확인된 뒤 데이터 풀을 넓힌다.

## 설계 근거

로컬 원문은 `Spotial_GUI_Design_Spec.md`이다. 과거 세 시나리오 중 이번 기본값은 사용자가 새로 지정한 지도·촬영 두 상황이다. 청크 탭 분기는 이번 설명을 적용하고, 규격서의 상단 대표 이미지 진입도 함께 지원한다.
